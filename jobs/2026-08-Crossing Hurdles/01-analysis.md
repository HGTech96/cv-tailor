# Stage 1 — JD Analysis

## Must-haves
- "Strong professional software engineering experience"
- "Strong hands-on coding experience in Python, with a deep understanding of data structures, algorithms, and system design"
- "Proven experience writing, reviewing, and debugging production-level code"
- "Strong written communication skills and a high attention to detail"
- Ability to "work completely independently and asynchronously, following detailed technical guidelines"

## Nice-to-haves
- None explicitly separated from must-haves in the posting — quals list reads as a single bar. Implicit preference for candidates comfortable evaluating AI-generated content specifically (not just writing their own code), and for engineers who can reason about correctness/efficiency/scalability/best-practice tradeoffs rather than just "does it run."

## ATS keywords
python, software engineering, data structures, algorithms, system design, code review, debugging, production-level code, code quality, correctness, efficiency, scalability, industry best practices, written communication, attention to detail, independent work, asynchronous, technical feedback, technical guidelines

## Seniority & scope signals
- No team size, management, or leadership language anywhere in the posting — this is a pure individual-contributor evaluator role.
- "Strong professional software engineering experience" (unquantified) plus hourly contract structure (5–20 hrs/week, up to $65/hr) signals they want senior/experienced ICs moonlighting on assessment work, not junior engineers and not people who need people-management credentials.
- Emphasis is on judgment and communication quality per task, not on ownership of a system over time.

## What they're really hiring for
They need experienced software engineers to act as graders and sparring partners for an AI model: reading Python code and technical explanations the model produced, catching where its logic, efficiency, or engineering judgment is wrong, and writing that critique up clearly enough that it can be used as a training signal. The real bar isn't "can you build a system" but "can you evaluate someone else's (the model's) code rigorously against correctness/efficiency/scalability/best-practices, and articulate why in structured written feedback" — with zero synchronous support, so self-directed rigor and communication precision matter more than any specific framework or domain.
